# 다우닝 행사 실적 대시보드 — 인수인계 문서

Claude.ai 채팅에서 여러 세션에 걸쳐 만든 대시보드입니다. Claude Code로 넘어가서
계속 작업하실 때, 아래 내용을 먼저 읽고 시작하시면 시행착오를 줄일 수 있어요.

## 1. 지금 뭐가 있는지

- **`event_pnl_dashboard.html`** — 메인 파일. 이거 하나가 전부입니다.
  데이터(JS 상수) + 렌더링 로직(JS 함수) + 화면(CSS)이 전부 이 파일 안에
  들어있어요. 별도 서버, 빌드 과정, 데이터베이스 없이 브라우저에서 파일
  하나만 열면 바로 동작합니다. (2026-09-04 기준 약 4,200줄, 9월 데이터까지 반영)

- 이 파일은 순수 정적 파일이라, 새 판매 데이터가 나올 때마다 **사람이 직접
  엑셀을 다시 올려서 다시 만들어야** 합니다. ERP 자동 연동은 아직 안 되어
  있고, PPT 로드맵에도 "장기 검토" 항목으로만 적어뒀어요.

## 2. 데이터 구조 (제일 중요)

### `EVENTS` 배열
행사 하나당 객체 하나. 핵심 필드:
```js
{
  name: "롯데노원 행사(07-10~07-19)",
  month: "2026-07",              // 종료월 기준
  channel: "백화점",              // 백화점 | 라운지 | 온라인 | 밀로티
  mall: "롯데노원",
  startDate: "2026-07-10",
  endDate: "2026-07-19",
  profitPlan: 0.16,  profitActual: 0.31,     // 억원
  revenuePlan: 0.40, revenueActual: 0.60,    // 억원 (백화점/밀로티만 유의미)
}
```

**정산완료 vs 진행중 판정 (`isSettled()`)** — 이거 한 번 크게 데인 부분이라
꼭 알아두세요:
```js
function isSettled(e){
  if (e.profitActual != null) return true;              // 데이터 있으면 무조건 완료
  if (e.partialRevenue != null) return false;            // 잠정치 필드 있으면 계속 진행중
  if (!e.endDate) return false;
  return new Date(e.endDate+"T23:59:59") <= new Date();  // 최후의 수단: 날짜 비교
}
```
**교훈**: "종료일이 지났는지"만으로 판정하면, 실제 시스템 날짜가 흐르면서
실적 데이터 없는 행사가 조용히 "정산완료 0원"으로 잘못 넘어가는 버그가
여러 번 났어요. **데이터 존재 여부를 항상 날짜보다 먼저 체크**하세요.

진행중 행사는 `partialRevenue`, `partialProfit`, `partialDays`, `totalDays`,
`partialTx` 필드로 "현재까지"를 표시합니다. `partialDays === 0`이면
"아직 시작 전(예정)" 상태로 자동 분류돼요 (`renderPending`이 "현재 진행중"
/ "행사 시작 전" 두 그룹으로 나눠서 보여줌 — 시작일이 지나 실제 데이터가
채워지면 별도 조작 없이 자동으로 그룹이 옮겨감).

### 채널별 성격이 완전히 다름
| 채널 | 비교 기준 | 이익 표기 | 비고 |
|---|---|---|---|
| 백화점 | 전년동기 (`isYoy:true`) | 상품이익율(%) | 매장별 1:1 그리디 매칭 |
| 라운지 | 전년동기 | 상품이익율(%) | 상품(모델) 단위, 매장별 개념 없음 |
| 밀로티 | 전년동기 | 상품이익율(%) | 매장별 1:1 그리디 매칭 |
| 온라인 | 계획(사전시뮬) | 상품이익율(%) | 실데이터는 롯데홈쇼핑만, 나머지 몰은 없음 |

`baselineMeta(channel)` 함수가 이 분기를 담당. **새 채널 추가하거나 로직
건드릴 때 여기부터 확인하세요.**

### 채널 전체 매출 관련 상수 (행사 무관, 참고용)
`CHANNEL_TOTAL_REVENUE`, `CHANNEL_MARGIN` (2026년), `CHANNEL_TOTAL_REVENUE_PRIOR`,
`CHANNEL_MARGIN_PRIOR` (2025년) — 채널×월 키. **새 월 추가할 때 여기 다
채워야 함.** 안 채우면 undefined 에러 남 (아래 "자주 나는 버그" 참고).

### 매장별 1:1 매칭 (전년동기)
백화점/밀로티는 `revenuePlan`/`profitPlan` 필드에 "같은 매장의 계절적으로
가장 가까운 2025년 행사" 실적이 미리 계산돼서 박혀있어요. **그리디 매칭**
(순서대로 하나씩 배정, 재사용 안 함) 방식이라 완벽한 최적해는 아니지만,
매장당 행사가 1~3개 수준이라 실용적으로 충분하다고 판단했어요.

⚠️ **날짜 매칭할 때 반드시 "계절성 기준"(연도 무시, 월-일만 비교)으로
거리를 재야 함.** 절대 날짜 차이로 재면 연도가 다른 두 날짜가 뒤집혀서
엉뚱한 게 매칭되는 버그가 실제로 났었어요.

### 품목 데이터
`PRODUCT_FULL_BY_STORE` — 매장×월별(6/7/8월 + "전체") 품목 성과.
`PRODUCT_BY_MONTH_CHANNEL` — 채널 전체 관점의 월별 품목 성과.
둘 다 "소파" 카테고리만 집계 대상(다른 카테고리는 품목 성과에서 제외).

취소율 계산은 **주문번호(정정 접미사 "-2","-3" 제거) + 품목명** 기준으로
그룹핑해서, 그 그룹의 순수량이 0 이하면 취소로 판정. (고객명 기준 아님 —
동명이인/재구매 오판 위험 때문에 일부러 이렇게 함.)

## 3. 온라인 채널 특수 로직

온라인은 실제 판매 로그(`ONLINE_ORDER_STATS`)가 월별로 있어서, **진행중
상태에서도 실시간에 가깝게 상세 분석(주문건수·객단가·판매량)이 가능**해요.
다른 채널(백화점 등)은 원래 "정산완료 건에만 상세분석 적용"이 원칙이었는데,
나중에 "진행중 이벤트의 partialRevenue도 실제 판매기록 기반이니 믿을만
하다"고 판단해서, 같은 로직(`buildGrowthTooltip`)에 진행중 이벤트를
`revenueActual`로 치환한 가상 리스트를 넣어 확장했어요. (`partialAsSettledList`
변수 검색하면 나옴)

롯데홈쇼핑은 `PRODUCT_MATCH_LOTTESHOPPING`(사전시뮬 vs 실적, 모델+사이즈
단위 매칭)이 따로 있어서 "계획대비" 상세분석도 가능. 다른 몰은 이 데이터가
없어서 계획대비 상세분석이 안 뜸(의도된 동작).

## 4. UI 핵심 컴포넌트

- **KPI 카드 4개** (`renderKpis`) — 정산완료 행사 수 / 실적 매출 / 전년(계획)
  매출 / 매출 달성률. 메인 숫자는 항상 매출(억원), 이익율은 서브텍스트로.
- **채널별 손익 비교** (`renderChannels`) — 계획/당월/전월/전년 최대 4박스.
  isYoy 채널은 3박스(계획 없음), 온라인은 4박스(전년 데이터 확보됨).
- **미니 분석 툴팁** (`buildGrowthTooltip` / `buildOnlineTooltip` /
  `buildOnlinePlanTooltip`) — 배지에 마우스 올리면 뜨는 "왜 이렇게 됐는지"
  자동 분석. 채널 성격별로 다른 함수 사용.
- **현재 행사 현황** (`renderPending`) — "현재 진행중" / "행사 시작 전" 2단
  구성. 진행중 카드엔 같은 매장의 **최근 완료 3건 중 기간이 가장 비슷한 것**을
  골라(단순 "가장 최근"이 아님 — 7일짜리와 14일짜리를 비교하면 왜곡되니
  기간 유사도까지 고려) 일평균 페이스를 증감률(%)로 비교. **마이너스면
  행사명 옆에 진한 빨강 "⚠ 점검필요" 배지가 자동으로 붙고, 플러스로
  바뀌면 다음 데이터 갱신 때 자동으로 사라짐** (파일을 새로 만들 때마다
  재계산되는 것이지 브라우저에서 실시간으로 바뀌는 건 아님). 최근 3건 중
  최선의 매칭도 기간 차이가 3일 넘게 나면 "⚠ 기간 차이 있음"이라고 솔직하게
  표시함.

### 디자인 시스템
CSS 변수(`:root`)에 색상 톤이 몰려있음. 헤더 배너 + KPI 카드는 흰 배경에
왼쪽 컬러바만(과하지 않게), 하이라이트류 카드(초과달성/미달성, TOP5/BOTTOM5,
품목별 성과)는 배경 자체를 톤온톤으로 채움(`card-good-tint`/`card-bad-tint`/
`card-indigo-tint`). 채널 구분은 색으로 안 하고(전부 인디고 통일) 텍스트로만
구분 — 색은 의미(인디고=중립, 초록=좋음, 빨강=주의)에만 씀.

**테두리는 일부러 두껍고(2px) 진하게(`--border:#A9B4CC`) 잡혀있음** — 밝은
발표 공간에서 카드 경계 자체가 안 보이는 문제가 있어서 의도적으로 강하게
잡은 것. 나중에 "너무 밋밋하다"고 얇게 되돌리고 싶어질 수 있는데, 그러면
같은 문제가 재발함.

## 5. 자주 났던 버그 (재발 주의)

1. **하드코딩된 월 배열** — `prevMonthBucket()`이 `["06","07","08"]`으로
   하드코딩되어 있어서 9월이 오자 "전월 없음"으로 오판. → 숫자 계산으로
   일반화해서 고침. **새 상수 만들 때 특정 월/연도를 배열로 하드코딩하지
   말 것.**
2. **`null` vs `undefined` 체크 누락** — `shareVal !== null`처럼 엄격
   체크만 하면 `undefined`일 때 못 잡아서 `.toFixed()` 호출 시 크래시.
   → `!= null`(느슨한 비교)로 null/undefined 둘 다 잡도록.
3. **판매일자 vs 주문번호 기준 불일치** — "주문번호 앞 6자리 = 주문일자"는
   신규 주문엔 맞지만, **취소/정정 건은 원래 주문번호를 유지한 채 처리일만
   바뀌는** 경우가 있어서 취소분이 엉뚱한 달로 새는 문제가 있었음.
   → 집계는 항상 **판매일자(raw 컬럼) 기준**으로 통일.
4. **가짜/예시 데이터를 실데이터로 오인** — 개발 초기에 만든 mock 이벤트에
   나중에 실제 매장 매출을 갖다 붙이는 실수가 있었음. → 코드에 "예시"라고
   써있으면 반드시 실제 존재 여부부터 확인.
5. **jsdom이 CSS 변수(`var(--bad)`)를 못 읽는 경우 있음** — 배경색 등
   중요한 스타일은 hex 값 직접 명시하는 게 안전.
6. **"진행중" 분기에서 채널 성격(계획형 vs 전년동기형) 구분 누락** — KPI
   서브텍스트나 라벨을 만들 때 `usingPartial`만 보고 무조건 "계획"이라는
   단어를 넣었다가, 백화점처럼 계획 개념 자체가 없는 채널에서 "전년 매출 -
   진행중 행사의 월간 전체 계획"처럼 말이 안 되는 문구가 나온 적 있음.
   → `meta.isYoy` 여부를 항상 먼저 분기할 것.
7. **매장 필터 조건이 "사용자가 명시적으로 선택했는지"만 체크하는 함정** —
   롯데홈쇼핑 계획대비 툴팁이 `state.malls`로 직접 선택했을 때만 뜨게
   해놨더니, "몰:전체"인데 실질적으로 데이터가 롯데홈쇼핑뿐인 경우엔 안
   뜨는 사각지대가 있었음. → 사용자의 필터 선택이 아니라 **현재 화면에
   실제로 반영된 데이터(`list`/`pendListCh`의 mall 목록)** 기준으로
   판단해야 함.
8. **툴팁 방향(tip-left/tip-right)을 채널 레이아웃 특성 고려 없이 하드코딩**
   — 온라인은 [계획→당월→전월→전년] 순서라 당월이 2번째 칸이라 왼쪽에
   여유가 있었지만, 백화점 등 전년동기형은 [당월→전년] 순서라 당월이
   맨 왼쪽 칸이라 "왼쪽으로 여는" 툴팁이 화면 밖으로 잘림. 방향 자체를
   채널별로 바꾸면 사용자가 원래 요구한 "왼쪽 배치"와 어긋나므로, **방향은
   유지하고 화면 경계를 넘으면 JS(`mouseover` 리스너, `transform:
   translate()`)로 필요한 만큼만 안쪽으로 밀어주는 방식**으로 해결함.
   (`.has-tip`에 이벤트 위임, `dataset.clamped`로 중복 실행 방지)

## 6. 데이터 갱신 워크플로우 (지금까지 해온 방식)

1. 회계팀이 ERP에서 "품목별판매현황" 엑셀(그룹명·품목코드·품목명·주문번호·
   매입처·판매점·고객명·판매일자·수량·매출액·실매출액·입고가·이익금·이익율·
   채널 컬럼 포함)을 다운로드해서 업로드
2. 영업지원팀 쪽 "행사 일정" 엑셀(매장·시작일·종료일)도 별도 업로드
3. 판매일자 기준으로 채널×월별 집계 + 매장×월별 품목 집계 + 매장별 1:1
   매칭을 Python으로 계산 → 결과를 JS 상수 형태로 만들어서 HTML에 삽입
4. `node -e "new Function(...)"` 로 문법 검증 → jsdom으로 전 채널×월
   순회하며 렌더링 에러 없는지 회귀 테스트 → 저장

이 전체 과정이 지금은 사람(저)이 매번 손으로 스크립트를 새로 짜는 방식이라,
자동화 파이프라인으로 만드는 게 다음 단계로 좋을 것 같아요.

## 7. 앞으로 필요한 것 (PPT 로드맵에서 가져옴)

## 9. Claude Code로 넘어올 때 참고

- **claude.ai/code(웹 버전)는 GitHub 저장소가 필수**라서 로컬 파일만
  가지고는 못 씀 — 반드시 **데스크톱 앱**(claude.ai/download)을 받아서
  로컬 폴더를 직접 열어야 함.
- Claude Code에서는 실제 브라우저로 스크린샷을 찍어서 눈으로 직접 확인
  가능(Playwright 등). 채팅에서는 이게 안 돼서 디자인 관련 요청은 매번
  캡처를 받아서 확인해야 했음 — Claude Code에서는 이 왕복을 줄일 수 있음.
- 새 판매 데이터 반영 요청이 오면: 엑셀에서 채널×월별 집계, 매장×월별
  품목 집계, 매장별 1:1 매칭(그리디, 계절성 기준 날짜 비교)을 재계산해서
  `EVENTS`/`CHANNEL_TOTAL_REVENUE` 등 JS 상수를 갱신하는 흐름을 그대로
  따라가면 됨 (본 문서 6번 항목 참고). 이 과정을 스크립트로 자동화하는
  게 이 프로젝트의 다음 단계로 가장 가치 있는 작업일 것 같음.
